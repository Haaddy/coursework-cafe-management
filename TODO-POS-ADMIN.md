## Часть A. Админ-панель: доступ только для менеджера

### Целевая логика

- **Бариста/POS**: без входа в админку. Может принимать заказ, отметить готовность, провести оплату и закрыть чек своим `employeeCode`.
- **Менеджер/Admin**: входит в админку как активный сотрудник с должностью `manager` / `менеджер`; после входа может смотреть статистику, управлять меню, складом, рецептами и сотрудниками.
- **Важно**: защита должна быть не только на фронте. Даже если пользователь откроет `/admin` руками, backend должен отклонять admin-запросы без менеджерской сессии.
- Старый UI `AdminUnlockModal` с “ключом администратора” можно заменить или переиспользовать как форму логина, но сам “ключ только на фронте” не считать безопасной авторизацией.
- **Упрощение для курсовой**: без cookie и без отдельного пароля в БД. Backend выдаёт простой session token, фронт хранит его в `localStorage` и отправляет в `Authorization: Bearer <token>`.

## Часть B. POS для баристы: номер заказа, оплата, закрытие чека кодом сотрудника

### Описание и спецификация (сервер, БД, API)

Ниже — целевая логика, на которую завязаны задачи B1–B4. Текущий код: `orders.id` (TEXT, UUID), поле `name`, `status`, списание склада при **создании** заказа в `ordersService.createOrder`; сотрудники в `employees` с уникальным `personal_code`.

#### `id` и `order_number`

- **`id`** — внутренний идентификатор: PK, связь `order_items`, движения инвентаря (`reference_id`), запросы `GET/PATCH/POST .../orders/:id`. На экране POS **не** показывать как «номер заказа».
- **`order_number`** — человекочитаемый номер для баристы и клиента (чек, список заказов). Генерировать **только на сервере** в той же транзакции, что и `INSERT` заказа (например счётчик заказов за календарный день + префикс даты, или другой выбранный формат — зафиксировать в B1.1 и в таблице «Заметки»).

#### Поле `name`

- Убрать смысл «имя клиента» с POS: тело `POST /orders` **без** обязательного имени; колонку `name` можно оставить для совместимости (пустая строка / `—` / копия номера) или постепенно вывести из API-ответа для новых заказов.

#### Жизненный цикл статусов (согласовать один вариант)

Рекомендуемая цепочка, если оплата **после** приготовления (проще стыкуется с текущей кнопкой «Отметить готовым»):

1. **`pending`** — заказ создан; склад уже списан при создании (**повторно не списывать** на шаге оплаты).
2. **`ready`** — готов к выдаче (аналог текущего статуса «готово»; лучше в БД хранить латиницу `ready`, в UI — «Готово»).
3. **`paid`** — эмуляция оплаты прошла, заполнены `payment_method`, `paid_at`.
4. **`closed`** — чек закрыт, заполнен `closed_by_employee_id` (и при необходимости `closed_at`).

Правила валидации на сервере: оплата только из допустимого статуса (например `ready` → `paid`); закрытие только из `paid` → `closed`. Для заказа уже в `closed` — идempotent-ответ или 409.

Альтернатива (если по сценарию «сразу при оформлении»): после `POST /orders` сразу шаг оплаты → `paid`, шаг «готово» опционален или идёт параллельно — тогда пересобрать переходы в B2.4 и на фронте (B3).

#### Эмуляция оплаты (данные + API)

- Колонки в `orders`: `payment_method` (TEXT: `cash`, `card`, `other`, …), `paid_at` (TEXT ISO). Отдельная таблица платежей не обязательна для курсовой.
- Эндпоинт (пример): `POST /orders/:id/pay` с телом `{ "paymentMethod": "cash" }` — проверка статуса, обновление полей, `status = 'paid'`, возврат полного объекта заказа.

#### Закрытие чека кодом сотрудника (данные + API)

- Эндпоинт (пример): `POST /orders/:id/close` с телом `{ "employeeCode": "…" }`.
- Логика: найти `employees` по `personal_code`, `status = 'active'`; опционально проверить `position` (бариста и т.д.); если заказ не `paid` — 400; записать `closed_by_employee_id`, перевести в `closed`. В ответе отдавать имя/ид сотрудника, закрывшего чек, для UI.

#### Слои реализации на сервере

1. `backend/src/data/database.js` — `ALTER TABLE` для существующей SQLite + при необходимости правка `CREATE TABLE` для новых установок.
2. `backend/src/services/ordersService.js` — генерация `order_number`, маппинг полей, `payOrder`, `closeOrderWithEmployeeCode`, обновление `updateOrderStatus` под единую модель статусов.
3. `backend/src/controllers/ordersController.js` и `backend/src/routes/orderRoutes.js` — новые маршруты и валидация тела запроса.

#### Нюансы

- **Legacy-заказы:** для старых строк без `order_number` — миграция данных или fallback при чтении (например отображать хвост UUID).
- **Язык статусов в БД:** один стиль (латиница), перевод только на фронте.
- **Базовый URL API:** сейчас фронт бьёт в `http://localhost:3001` — при доработке вынести в константу.
